# AGENT_PLAYBOOK.md — Как работать над проектом «Камыш»

Дополнение к [`AGENTS.md`](../AGENTS.md). Здесь не идеалы, а **рабочий процесс**: что реально
приводило к результату в этом репозитории и какие грабли уже наступили.

`AGENTS.md` отвечает на вопрос «что можно и что нельзя».
Этот файл отвечает на вопрос «как именно действовать, чтобы не переделывать».

---

## 0. Главное правило

> **Не заявляйте о результате, который не проверили.**

Проект легко собирается в режиме, где всё «зелёное», но ничего не работает: моки
возвращают правдоподобные ответы, тесты проходят, а реального пути нет. Задача считается
выполненной, когда вы **видели**, как данные проходят через систему целиком, а не когда
компилятор не ругается.

Критерий: если вас спросят «покажи, что это работает», у вас должен быть конкретный
вывод команды — не ссылка на код, а результат прогона.

---

## 1. Разведка перед действием

Перед первой правкой в незнакомой области:

1. **Прочитайте, что уже есть.** В этом репозитории почти каждая задача реализуется
   на 60–80% существующим кодом. Прежде чем писать новый модуль, ищите:
   - трейт или структуру, которая уже это делает;
   - готовый API-хендлер и UI-страницу;
   - миграцию или репозиторий для новой сущности.
2. **Проверьте документацию SSOT** (`docs/`). Если код и документация расходятся —
   доверяйте коду, но расхождение зафиксируйте.
3. **Проверьте, что «уже работает» — действительно работает.** В этом проекте
   встречались `AtomicBool::new(true)` вместо реальной проверки устройства и
   провайдеры, которые «поддерживаются», но их бинарника нет в PATH.

### Как искать

Используйте поиск по содержимому и по путям (`grep`/`glob`-инструменты), а не
`find` в оболочке. Читайте файл целиком, если он меньше ~300 строк: контекст
важнее пары сэкономленных запросов.

## 2. Цикл работы

```text
[1. Разведка] ──► [2. План] ──► [3. Реализация] ──► [4. Проверка] ──► [5. Отчёт]
```

### 2.1. План

Составьте список шагов и держите его актуальным. Это не бюрократия: на задачах
вроде «подключить захват микрофона» шагов больше десяти, и без списка агент
теряет, на каком он этапе.

Каждый шаг формулируйте как **проверяемый результат** («распознаёт фразу из WAV»),
а не как действие («написать код для STT»).

### 2.2. Реализация

- **Правки атомарные.** Одна мысль — одна правка. Не переписывайте файл, если можно
  заменить блок.
- **Сначала компиляция, потом всё остальное.** Дешёвый цикл `cargo check` держите
  в приоритете: он ловит 90% ошибок за секунды.
- **Не трогайте тесты, чтобы они прошли.** Если тест упал из-за вашей правки — прав
  тест, а не вы. Единственное исключение: тест утверждает **неверное поведение**
  (как это было с `microphone_available: true` в `/api/v1/speech/status`). В этом
  случае исправляйте тест осознанно и объясняйте в отчёте, почему старое
  утверждение было ошибочным.

### 2.3. Проверка

Полный набор обязательных проверок — в `AGENTS.md`, раздел 3. Добавлю то, чего там нет:

- **Проверяйте на уровне, где живёт ошибка.** Компиляция ловит типы, но не логику.
  Для новой подсистемы запускайте её через реальный API, а не только юнит-тестом.
- **Один тест — не доказательство.** `cargo test` зелёный может означать, что тест
  проверяет заглушку. Пробейте путь до конца: HTTP-запрос → реальный результат в БД.
- **Считайте тесты.** Зафиксируйте число до и после. Новая функциональность без
  новых тестов — почти всегда недоделка.

## 3. Окружение этого проекта (важно)

Здесь собраны грабли, которые уже стоили времени. Не повторяйте.

### 3.1. Windows-хост + WSL2

Целевое железо — **ARM64** (целевой микрокомпьютер), разработка идёт на **x86_64 Windows + WSL2**.
Прямая сборка в Windows не работает.

**Симптом:** `error: error calling dlltool 'dlltool.exe': program not found`.

**Причина:** активный toolchain — `x86_64-pc-windows-gnu`, а `gcc.exe`/`dlltool.exe`
в системе нет.

**Решение:** собирайте в WSL2 (Ubuntu), там есть Rust и gcc:

```bash
wsl
cd /mnt/m/Project/Kamish-os/radiant-bardeen
export CARGO_TARGET_DIR=$HOME/.cache/kamish-target   # не в /mnt — там медленно
cargo check --workspace --all-targets
```

Выносить `CARGO_TARGET_DIR` в домашний каталог WSL обязательно: сборка в `/mnt/m/...`
идёт в разы медленнее из-за файловой системы.

### 3.2. Кавычки в WSL-командах

**Симптом:** команда выполняется, но вывод пустой; или `Syntax error: Unterminated
quoted string`; или JSON-кавычки «съедаются».

**Причина:** многослойное экранирование `pwsh → wsl → sh -lc`. Кавычки проходят
через два парсера и теряются.

**Решение:** для любой команды длиннее одной строки или содержащей кавычки —
**пишите скрипт в файл** и запускайте файл. Не воюйте с экранированием.

```powershell
# плохо: кавычки сломаются
wsl -e sh -lc "curl -d '{\"a\":\"b\"}' ..."

# хорошо: скрипт в репозитории, запуск файлом
wsl -e sh /mnt/m/Project/Kamish-os/radiant-bardeen/scripts/проверка.sh
```

### 3.3. PowerShell может склеить файл в одну строку

**Симптом:** `cargo test` пишет `running 0 tests` для файла, где тесты точно есть.

**Причина:** `Set-Content` без `-Raw`/с неправильными переводами строк схлопывает
файл в одну строку. Rust такое иногда проглатывает без ошибки.

**Решение:** для правок файлов используйте `edit`/`write`, а не `Set-Content`.
После `Set-Content` всегда проверяйте число строк:

```powershell
Get-ChildItem -Recurse -Include *.rs -File | ForEach-Object {
  if ((Get-Content $_.FullName).Count -le 2) { "ПОДОЗРИТЕЛЬНО: $($_.FullName)" }
}
```

### 3.4. Сеть: не доверяйте одиночному `curl`

**Симптом:** `curl -o /dev/null` возвращает `000` для `pypi.org` и `huggingface.co`,
из чего легко сделать вывод «сети нет».

**Реальность:** `pip install` и скачивание с HF при этом работают. Пробный запрос
без VPN/прокси не показателен.

**Правило:** прежде чем объявить ресурс недоступным, проверьте **целевой операцией**
(`pip install`, фактическое скачивание), а не HEAD-запросом.

Отдельно: `alphacephei.com` (модели Vosk) отдаёт файл медленно и обрывает длинные
соединения без VPN. Используйте `curl -fL --retry 3 --retry-all-errors`.

### 3.5. Микрофон и звук в WSL2

- WSL2 **не пробрасывает** ни микрофон, ни Bluetooth-адаптер хоста.
- Для разработки используйте `KAMISH_AUDIO_SOURCE=mock`.
- Реальная проверка голосового ввода возможна только на целевом железе с Kamish Linux (Buildroot).
- Не заявляйте, что «микрофон работает», если проверяли мок.

### 3.6. Модели и внешние бинарники

| Компонент | Где искать | Что ожидает код |
|---|---|---|
| Piper TTS | `pip install piper-tts` | `PIPER_BIN`, `PIPER_MODEL_PATH` (`.onnx`) |
| Vosk STT | `pip install vosk` + модель | `VOSK_MODEL_PATH`, бинарник `vosk-transcriber` |
| Antigravity CLI | GitHub releases | `agy` в `PATH` или `/opt/kamish/bin` |

**Ловушка:** pip-пакет `vosk` **не устанавливает** бинарник `vosk-transcriber`,
которого ждёт `VoskSttProvider`. В репозитории лежит обёртка
[`scripts/vosk-transcriber`](../scripts/vosk-transcriber) — она нужна, иначе STT молча
уходит в mock.

Установка моделей одной командой: `scripts/install-local-models.sh`.

## 4. Эмуляция вместо железа

Проект принципиально не изображает несуществующее железо. Соблюдайте это:

1. **Мок обязан называться мок-ом.** `MockAudioSource` возвращает `name() == "mock"`
   и честно сообщает `unavailable_reason()`.
2. **Флаг доступности — результат проверки, а не константа.**
   `ArecordAudioSource::is_available()` смотрит на наличие бинарника.
   Если устройства нет — `false`, и это видно в API.
3. **Никакой подмены в статусах.** Если захват не запущен —
   `microphone_listening: false`, даже если это выглядит менее впечатляюще.
4. **Заглушка помечается в ответе.** `scripts/agy-mock` на `--version` отвечает
   `Antigravity CLI v1.0.0 (mock)`, а на любой запрос возвращает фиксированную
   строку `Antigravity CLI: alarm set for 07:30.` — это должно быть видно
   вызывающей стороне. Если ответ на разные вопросы всегда одинаковый — работает
   мок, а не модель.

Признак нарушения: в отчёте написано «работает», а в коде — `unwrap_or(true)`.

## 5. Типичные ошибки этого репозитория

Проверяйте себя по этому списку перед сдачей.

| Ошибка | Симптом | Как избежать |
|---|---|---|
| Константа вместо проверки | подсистема всегда «готова» | перечитывать статус после реального запуска |
| Провайдер без бинарника | `is_available()` врёт | проверять `find_binary()` и тестировать оба исхода |
| Тест проверяет заглушку | зелёный, но пути нет | прогонять через настоящий HTTP/CLI |
| `async fn` в трейте | `Box<dyn Trait>` не собирается | использовать `BoxFuture<'_, T>` |
| Обрезка файла при правке | `running 0 tests` | `edit` вместо `Set-Content`, проверка числа строк |
| Кэш сборки в `/mnt` | сборка в 10 раз медленнее | `CARGO_TARGET_DIR=$HOME/.cache/...` |
| Парсинг JSON через grep | тег = URL | якорить на поле: `grep -o '"tag_name"\s*:\s*"[^"]*"'` |

## 6. Отчёт

Шаблон — в `AGENTS.md`, раздел 5. Поверх него:

- **Числа, не прилагательные.** «113 тестов, 0 падений» вместо «тесты проходят».
- **Отделяйте проверенное от предположенного.** Если вы не смогли проверить
  авторизацию внешнего CLI — так и напишите: «не проверено, требует реального
  бинарника».
- **Перечисляйте ограничения.** Мок-режимы, недоступное железо, непроверенные пути.
  Это не признание слабости — это то, что позволяет пользователю вам доверять.
- **Давайте команду проверки.** Пользователь должен суметь воспроизвести результат
  без вашей помощи.

### Тон

- Пишите по-русски, если пользователь пишет по-русски.
- Без «Отлично!», «Конечно!» и эмодзи в начале абзацев.
- Если пользователь ошибается — скажите прямо и объясните, почему.
- Если задача невыполнима в текущих условиях — скажите это **до** того, как
  потратите час на частичное решение.
